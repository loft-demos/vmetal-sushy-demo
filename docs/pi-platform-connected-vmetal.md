# Pi Platform with Connected vMetal Host

This is the advanced topology for running vCluster Platform on the Raspberry Pi
cluster while keeping the vMetal host as the bare-metal provisioning site.

The important split is:

- vCluster Platform runs on the Pi cluster at `https://vcp.lab.kurtmadel.com`.
- Tenant vCluster control planes run on the Pi worker nodes.
- The vMetal host is connected to Platform as a separate Control Plane Cluster.
- The Metal3 `NodeProvider` points at the connected vMetal host, not at the Pi
  cluster.
- Metal3, Ironic, DHCP, Multus, Sushy Tools, libvirt, and the BareMetalHosts
  stay on the vMetal host side.

That gives you realistic separation: the tenant control plane is no longer
co-located with the virtual bare-metal machines it provisions.

## Target Topology

```text
DNS: vcp.lab.kurtmadel.com -> 192.168.50.10

Raspberry Pi cluster
  - 1 control-plane node
  - 2 worker nodes
  - MetalLB owns 192.168.50.10 - 192.168.50.20
  - Gateway / HTTPRoute exposes vCluster Platform
  - tenant vCluster control-plane pods are scheduled onto Pi workers

vMetal host
  - connected to Platform as a Control Plane Cluster
  - libvirt/KVM VMs attached to br-provision
  - Sushy Tools on 172.22.0.1:8000
  - OS image server on 172.22.0.1:9000
  - Metal3 / Ironic / DHCP / Multus deployed by the NodeProvider
```

## DNS and Gateway

Use the real Platform FQDN everywhere:

```bash
VCP_LOFT_HOST=vcp.lab.kurtmadel.com
```

The DNS record should resolve to the Pi cluster MetalLB address:

```text
vcp.lab.kurtmadel.com A 192.168.50.10
```

MetalLB on the Pi cluster should reserve that same IP for the Gateway service.
The HTTPRoute for Platform should accept `vcp.lab.kurtmadel.com` and route to
the `vcluster-platform` service.

With that in place, the repo's dnsmasq and Mac `/etc/resolver` flow is no
longer part of the Platform access path. Home and Tailscale access both work as
long as clients can route to `192.168.50.10`; if remote Tailscale clients are
off-LAN, make sure the Pi LAN is advertised through a Tailscale subnet router or
use a Tailscale-reachable address for the DNS record.

If the home LAN later changes to `172.29.137.0/23`, the Pi MetalLB address and
DNS record will need to move together. Keep the vMetal provisioning network on a
different CIDR, such as the repo default `172.22.0.0/24`, to avoid overlap.

## Remove Platform from the vMetal Host

Do this only after the Pi-hosted Platform is reachable and you have confirmed
you can log in at `https://vcp.lab.kurtmadel.com`.

On the vMetal host, remove the old standalone Platform install:

```bash
curl -sfL https://github.com/loft-sh/vcluster/releases/latest/download/install-standalone.sh \
  | sudo sh -s -- --reset-only
```

This removes the local standalone Platform cluster from the vMetal host. It does
not remove libvirt VMs, Sushy Tools, the provisioning bridge, or the local image
server.

Keep these host-side pieces:

```bash
bash scripts/create-bridges.sh
bash scripts/install-sushy-service.sh
bash scripts/install-image-server.sh
```

## Connect the Clusters

Connect both clusters to the Pi-hosted Platform:

- the Pi cluster, as the place tenant control planes should run
- the vMetal host, as the infrastructure cluster where Metal3 manages hardware

Use clear cluster names in Platform. The examples below assume:

```text
pi-lab
vmetal-host
```

The exact connect command is generated by the Platform UI for each cluster.
After connecting, verify from the Platform cluster context:

```bash
kubectl get clusters.management.loft.sh
```

## Schedule Tenant Control Planes on Pi Workers

Label the two Pi workers:

```bash
kubectl label node <pi-worker-1> vcluster.loft.sh/private-control-plane=true
kubectl label node <pi-worker-2> vcluster.loft.sh/private-control-plane=true
```

Optionally taint them if you want to reserve them for vCluster control planes:

```bash
kubectl taint node <pi-worker-1> vcluster.loft.sh/private-control-plane=true:NoSchedule
kubectl taint node <pi-worker-2> vcluster.loft.sh/private-control-plane=true:NoSchedule
```

Then add scheduling rules to the vCluster template Helm values:

```yaml
controlPlane:
  statefulSet:
    scheduling:
      nodeSelector:
        vcluster.loft.sh/private-control-plane: "true"
      tolerations:
        - key: vcluster.loft.sh/private-control-plane
          operator: Equal
          value: "true"
          effect: NoSchedule
      topologySpreadConstraints:
        - maxSkew: 1
          topologyKey: kubernetes.io/hostname
          whenUnsatisfiable: ScheduleAnyway
          labelSelector:
            matchLabels:
              app: vcluster
```

For the repo's dynamic template, this belongs in
`manifests/platform/vmetal-template.yaml` under:

```yaml
spec:
  template:
    helmRelease:
      values: |
        controlPlane:
          statefulSet:
            scheduling: ...
```

The `VirtualClusterInstance` should point at the Pi cluster:

```yaml
spec:
  clusterRef:
    cluster: pi-lab
```

This is what keeps the tenant vCluster control plane on the Pi workers.

## Point the Metal3 NodeProvider at vMetal

The Metal3 `NodeProvider` should point at the connected vMetal host:

```yaml
apiVersion: management.loft.sh/v1
kind: NodeProvider
metadata:
  name: us-va-blacksburg-dc1
spec:
  metal3:
    clusterRef:
      cluster: vmetal-host
      namespace: metal3-system
```

This is intentionally different from the `VirtualClusterInstance.clusterRef`.

- `VirtualClusterInstance.clusterRef.cluster: pi-lab` means the tenant control
  plane runs on the Pi cluster.
- `NodeProvider.spec.metal3.clusterRef.cluster: vmetal-host` means Metal3,
  Ironic, DHCP, Multus, and BareMetalHosts live on the vMetal host.

Keep the existing provider network settings unless you change the provisioning
bridge:

```yaml
deploy:
  dhcp:
    enabled: true
    helmValues: |
      networkAttachmentDefinition:
        vip: 172.22.0.2/24
        config: |
          {
            "cniVersion": "0.3.1",
            "type": "bridge",
            "bridge": "br-provision",
            "ipam": {}
          }
```

## Platform URL Reachability from Provisioned Nodes

Provisioned private nodes still need to reach Platform at
`https://vcp.lab.kurtmadel.com`.

With the new DNS entry, BareMetalHost DNS no longer needs to know a private
`vdemo.local` zone. You can either:

- point `metal3.vcluster.com/dns-servers` at normal LAN DNS that resolves
  `vcp.lab.kurtmadel.com`, or
- keep using the vMetal host bridge IP `172.22.0.1` if you still want the host
  to forward DNS for provisioned nodes.

The nodes must also be able to route from `172.22.0.0/24` to `192.168.50.10`.
The repo's `scripts/create-bridges.sh` NAT rule handles this through
`LAN_INTERFACE`.

If you later move the home LAN to `172.29.137.0/23`, verify:

```bash
dig +short vcp.lab.kurtmadel.com
sudo iptables -t nat -L POSTROUTING -n | grep 172.22
```

The first command should return the new Pi MetalLB IP, and the second should
still show NAT for the provisioning CIDR.

## Apply Order

1. Install and expose vCluster Platform on the Pi cluster at
   `https://vcp.lab.kurtmadel.com`.
2. Verify DNS returns `192.168.50.10` and the Platform UI is reachable.
3. Remove vCluster Platform from the vMetal host with `--reset-only`.
4. Keep or recreate the vMetal host infrastructure: `br-provision`,
   Sushy Tools, image server, and demo VMs.
5. Connect the Pi cluster and vMetal host to the Pi-hosted Platform.
6. Update `VirtualClusterInstance.clusterRef.cluster` to the Pi cluster name.
7. Update `NodeProvider.spec.metal3.clusterRef.cluster` to the vMetal connected
   cluster name.
8. Apply the NodeProvider and wait for Metal3/Ironic/DHCP to become ready.
9. Apply BareMetalHosts on the vMetal connected cluster namespace.
10. Create the private-node vCluster from the template.

## Validation

From the Platform management context:

```bash
kubectl get clusters.management.loft.sh
kubectl get nodeprovider us-va-blacksburg-dc1
kubectl get virtualclusterinstances -n p-default
```

From the vMetal connected cluster context:

```bash
kubectl get pods -n metal3-system
kubectl get baremetalhosts -n metal3-system
curl http://172.22.0.1:8000/redfish/v1/Systems/
curl -I http://172.22.0.1:9000/ubuntu-24.04-minimal-cloudimg-amd64.img
```

From a provisioned private node:

```bash
resolvectl query vcp.lab.kurtmadel.com
curl -I https://vcp.lab.kurtmadel.com
```

The expected end state is a vCluster whose control-plane pods run on the Pi
workers while its private nodes are provisioned as vMetal-managed machines from
the vMetal host.
